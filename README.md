# Smart-NESMA · 软件需求与功能点管理

[English](./README-en.md) · [GitHub](https://github.com/coder-lulu/smart-nesma) · [许可证](./LICENSE) · [上游归属](./NOTICE)

Smart-NESMA 是面向软件需求梳理、功能点记录与评估协作的 Web 工作台，由蜂巢工作室维护。项目基于 Gin-Vue-Admin 扩展，将项目、建设周期、需求版本、L1–L4 需求树、功能点记录、分析任务和交付文档组织在同一套界面中。

适合需要把 Excel 需求清单转为结构化需求、维护不同建设周期的功能范围，以及整理软件计量材料的团队。AI 分析提供辅助入口，计量口径、功能边界和最终结果仍需人工审核。

![Smart-NESMA 工作台](docs/screenshots/01-workspace.png)

> 截图来自独立的脱敏演示数据，展示界面与功能组织；不代表 AI 服务、计算结果或完整业务流程已经通过端到端验收。本仓库不包含原始业务数据库备份、实际业务附件或运行凭证。

## 已实现的功能

下表中的“已实现”指代码中存在页面、接口及相应业务处理路径，不等于每种输入与异常分支均经过完整验收。涉及外部 AI 和模拟数据的能力另列在后文。

| 模块 | 已实现内容 | 使用价值 |
| --- | --- | --- |
| 项目管理 | 项目新建、查询、编辑、删除，项目详情和统计卡片 | 集中维护业务项目及其需求范围 |
| 建设周期 | 周期新建、编辑、删除、状态维护和激活周期切换 | 按建设阶段组织需求与分析 |
| 需求版本 | 周期内版本创建、查询、编辑、删除、激活版本设置、版本号及统计维护 | 为需求清单保留明确的版本归属 |
| 层级需求 | L1–L4 父子结构、表格筛选、增删改查、排序与移动接口 | 从业务模块逐层拆解到功能点计数项 |
| Excel 导入 | 需求表格解析、层级构建、项目/周期/版本关联、导入批次记录 | 将既有清单纳入统一管理；应按页面提供的模板准备表格 |
| 功能点字段 | EI、EO、EQ、ILF、EIF 分类，复杂度、AFP、UFP、重用程度、修改类型等字段维护 | 记录计量依据和人工确认的结果 |
| 评估记录 | 评估列表、创建入口、详情展示、功能点明细和调整因子界面 | 集中查看评估材料；自动计算存在模拟分支，详见限制 |
| 文档与模板 | 文档记录增删改查、预览、下载、单个/批量生成；模板维护和上传入口 | 组织需求与评估交付物，包含 Word/Excel 生成路径 |
| 知识库 | 知识条目增删改查、分类、标签及列表查询 | 沉淀领域说明和可复用计量参考 |
| 管理基础 | 用户、角色、菜单、接口权限与操作日志等上游后台能力 | 为不同使用者提供管理入口及访问控制基础 |

### L1–L4 需求与功能点

系统以项目为范围、周期为阶段、版本为归属，使用父子关系组织需求。L1–L4 是本项目的数据组织方式，不应直接当作 NESMA 标准的完整定义。

| 层级 | 系统含义 | 演示示例 |
| --- | --- | --- |
| L1 | 一级功能模块 | 客户服务 |
| L2 | 二级功能模块 | 工单管理 |
| L3 | 三级功能模块 | 工单受理 |
| L4 | 功能点计数项 | 新增工单、查询工单、工单数据维护 |

每条需求可以维护标题、描述、优先级、状态、分类、业务价值、验收标准、预计/实际工时及备注。L4 计数项进一步记录功能类别、复杂度、重用程度和新增/优化/删除等修改类型。

系统使用以下功能类别标识，具体归类应结合应用边界、数据维护责任和基本处理过程进行审核：

| 标识 | 名称 | 审核时关注的内容 |
| --- | --- | --- |
| EI | 外部输入 | 输入数据对内部数据或系统行为的维护作用 |
| EO | 外部输出 | 对外输出中的计算、派生或其他处理 |
| EQ | 外部查询 | 输入与检索输出组成的查询过程 |
| ILF | 内部逻辑文件 | 由应用维护的逻辑相关数据集合 |
| EIF | 外部接口文件 | 应用引用、由其他应用维护的数据集合 |

AFP（调整后功能点）与 UFP（未调整功能点）在本项目中是可保存、展示和用于汇总的字段。存在这些字段并不证明某个评估结果已经满足指定版本的计量标准。自动识别、复杂度判断、权重、调整因子和重复计数检查均应由计量人员复核；不要直接用演示数值形成报价、审计结论或正式计量报告。

### 建议的使用流程

1. 创建项目，填写业务背景，再设置建设周期和需求版本。
2. 手工维护需求，或按导入模板上传 Excel；检查层级、归属、重复项和导入结果。
3. 在需求树中补充 L1–L3 描述，将可计数的过程与数据组织为 L4 项。
4. 维护功能类别、复杂度、重用/修改类型以及 AFP/UFP 字段，记录计量依据。
5. 如需 AI 辅助，先配置服务，再对输出进行人工审核。不要把模拟结果当作模型推理或正式计量。
6. 查看评估记录，检查汇总范围和明细，再生成、预览和下载交付文档。

## AI 能力与当前边界

### 已接入代码、需要外部服务的能力

项目包含需求描述优化、L3 分析、L4 生成、Mermaid 流程图生成、项目分析、对话及批量任务相关界面与服务代码。实际 AI 请求由后端的 `ai_service.go`、`ai_service_manager.go` 等处理，需要自行配置可用的服务地址、模型及密钥。接口可访问与页面可打开，不代表模型调用已成功。

`server/config.example.yaml` 提供 DeepSeek、OpenAI 及 embedding 配置段。只有明确需要使用的服务才应填写真实凭证；凭证放入本地 `server/config.yaml`，不要提交到 Git。启用外部分析时，选中的需求内容会进入相应分析服务，使用者应确认数据可以发送。

## 系统架构

前端使用 Vue 3、Vite、Element Plus、Pinia 和 ECharts，后端使用 Go、Gin、GORM。NESMA 业务代码位于独立的前后端模块中，复用 Gin-Vue-Admin 的管理基础。

```mermaid
flowchart TB
    U[浏览器] --> W[Vue 3 / Element Plus 工作台]
    W -->|HTTP API| G[Gin 路由 / 身份认证 / 权限]
    W -.->|WebSocket| T[任务进度与对话]
    G --> S[项目 / 周期 / 版本 / 需求服务]
    G --> E[评估 / 文档 / 知识服务]
    G --> A[AI 服务适配层]
    T --> A
    S --> O[GORM]
    E --> O
    O --> P[PostgreSQL / pgvector]
    E --> F[本地文件与文档模板]
    A -.-> M[外部模型服务]
    A -.-> B[Embedding 服务或 mock 路径]
    G -.-> R[可选 Redis]
```

| 目录 | 用途 |
| --- | --- |
| `web/src/view/nesma/` | NESMA 业务页面与组件 |
| `web/src/api/` | 前端 API 请求封装 |
| `server/api/v1/nesma/` | 请求处理与响应 |
| `server/router/nesma/` | 业务路由注册 |
| `server/service/nesma/` | 项目、需求、评估、AI、文档等业务服务 |
| `server/model/nesma/` | 数据模型与请求/响应结构 |
| `server/config.example.yaml` | 去除真实凭证的配置模板 |
| `docs/screenshots/` | README 使用的脱敏演示截图 |

## 本地运行

### 环境准备

- Go **1.23 或更新版本**；`server/go.mod` 指定 `go 1.23`、工具链 `go1.23.9`。
- Node.js **22 或更新版本**，以适配锁定依赖中的较新工具。
- pnpm，使用仓库内的 `web/pnpm-lock.yaml` 安装依赖。
- 可连接的 PostgreSQL，数据库服务器安装 **pgvector** 扩展。可以复用已经运行的 Docker PostgreSQL 容器。
- Redis 是可选项；示例配置中 `system.use-redis` 为 `false`。

以下命令从仓库根目录开始，适用于 PowerShell 或具有相应命令的 shell。启动步骤依据当前源码入口及配置编写；全新环境安装和空库初始化尚未作为独立端到端流程完整验收。需要用户环境参数的数据库恢复命令未在共享数据库上重复执行。

### 1. 准备配置

仅在尚未创建本地配置时复制模板，避免覆盖已有设置：

```sh
cp server/config.example.yaml server/config.yaml
```

编辑 `server/config.yaml`：

| 配置项 | 设置说明 |
| --- | --- |
| `system.db-type` | 使用 `pgsql` |
| `system.addr` | 默认后端端口 `8888` |
| `pgsql.path` / `pgsql.port` | 数据库主机与 Docker 对宿主机发布的端口；模板中的 `5435` 是示例，不保证与你的容器一致 |
| `pgsql.username` / `pgsql.password` | 为本项目准备的数据库连接凭证 |
| `pgsql.db-name` | 已恢复的项目数据库名；全新初始化流程暂时设为空字符串，见下文 |
| `jwt.signing-key` | 替换为本地生成的独立随机密钥 |
| `ai.*` | 仅在使用外部 AI 时配置实际服务和密钥 |

后端在宿主机上运行时，通常连接 `127.0.0.1` 与容器发布端口；数据库容器内部端口通常为 `5432`。不要把示例端口、占位凭证直接当作已配置完成。

### 2. 准备数据库

**已有 Docker PostgreSQL 与自备备份：**

在现有实例中为 Smart-NESMA 使用独立数据库。服务器必须已安装与 PostgreSQL 版本匹配的 pgvector，并在目标数据库中启用 `vector` 扩展；仅安装普通 PostgreSQL 镜像不保证包含它。

如果拥有本项目的合法备份，可使用 PostgreSQL 的 `pg_restore` 恢复 custom-format `.dump`，指定目标数据库，并按本地角色配置使用 `--no-owner`、`--no-privileges`。备份恢复目标应是专门准备的空库。不要将 `globals.sql` 导入共享实例来覆盖已有角色、密码或权限，也不要对共享数据库执行清理恢复。具体容器名、用户、端口和备份路径由你的环境决定，因此这里不提供会直接修改未知实例的复制即执行命令。

恢复完成后，将 `pgsql.db-name` 设为目标库名，再启动后端。本公开仓库不提供业务 `.dump`、SQL 数据备份或真实账号密码。

**没有备份，使用全新初始化：**

先将 `pgsql.db-name` 设置为 `""`，保留 `system.db-type: pgsql`，再启动后端与前端。打开页面进入数据库初始化向导，填写 PostgreSQL 连接信息及准备使用的数据库名，完成基础表和初始化数据创建。初始化后检查生成的配置，并重启后端以加载 NESMA 表和服务。目标数据库仍需具备 `vector` 扩展及所需建表权限。

如果直接把不存在的数据库名填入 `pgsql.db-name`，后端会尝试连接并可能在向导可用前退出。菜单可见性由初始化数据及角色权限决定；如果 NESMA 页面入口未出现，请检查菜单和角色授权，不要为此导入他人的运行数据库。

### 3. 启动后端

在仓库根目录打开一个终端：

```sh
cd server
go mod download
go run .
```

默认服务地址为 <http://127.0.0.1:8888>，接口文档为 <http://127.0.0.1:8888/swagger/index.html>。后端需要从 `server` 目录读取本地配置和资源。

### 4. 启动前端

在仓库根目录另开一个终端：

```sh
cd web
pnpm install --frozen-lockfile
pnpm serve
```

访问 <http://127.0.0.1:8080>。开发环境由 `web/.env.development` 设置：前端 `8080`、后端 `8888`，`/api` 由 Vite 代理到后端。端口变更时同时调整前后端配置。

`pnpm serve` 会先运行上游的 `openDocument.js`，在部分桌面系统打开上游文档页，然后启动 Vite。登录使用自己初始化或恢复的账号；仓库不发布真实环境的登录凭证。

需要前端生产构建时，在 `web` 目录执行：

```sh
pnpm build
```

产物位于 `web/dist/`。正式部署还需要自行配置静态文件服务、API 代理和文件目录权限；本节描述的是本地开发启动。
